## P1 数据正确性与数据安全

### P1-1 Provider 路径迁移缺少事务与回滚

- 状态：已完成
- 位置：`packages/server/src/utils/provider-paths.ts`
- 问题：迁移先移动数据，最后写 `config.json`；中途失败时已移动部分不会整体回滚。
- 额外风险：SQLite 迁移只处理主 `.sqlite`/`.db`，没有处理 `-wal` 和 `-shm`，可能漏迁尚未 checkpoint 的数据。
- 目标方案：迁移前 preflight；生成 migration journal；目录迁移支持 rollback；配置在数据确认成功后提交；活动 SQLite 使用 SQLite backup API 或先安全 checkpoint 后迁移完整数据库。
- 验收：模拟目标冲突、跨盘复制中断、配置写失败、WAL 未 checkpoint 和进程中断，源数据保持可用且不会出现半迁移状态。
- 实现：采用 prepare/config commit/staging cleanup 两阶段流程；SQLite 使用 backup API 和 `quick_check`；配置写失败逆向 rollback；提交后 staging 清理失败改为成功结果中的诊断 warning。
- 验证：Codex WAL、活动 SQLite、OpenCode 内嵌 DB 组合迁移、目标冲突回滚和目录迁移测试通过。

### P1-2 JSONL 消息编辑/删除不是原子替换

- 状态：已完成
- 位置：`packages/server/src/utils/message-actions.ts`
- 问题：临时文件完成后使用 `copyFile` 覆盖原文件，不是同目录原子替换；进程中断或 CLI 并发追加可能造成截断或丢数据。
- 目标方案：同目录临时文件写入、flush、可选 fsync 后使用原子 rename；保留失败临时文件诊断信息；写前检查源文件 revision。
- 验收：写入期间进程退出、磁盘错误、外部追加和连续编辑/删除测试均不能产生半截 JSONL 或覆盖新行。
- 实现：同目录临时文件写入、flush/fsync、revision 校验和原子 rename；外部修改返回 `409`。

### P1-3 当前 mutation lock 只覆盖单进程

- 状态：已完成
- 位置：`packages/server/src/utils/mutation-queue.ts`
- 问题：进程内 `Map` 无法协调 UI server、title CLI、独立 ChatLog Viewer 进程与原生 CLI。
- 目标方案：增加跨进程 advisory lock/lockfile；所有 read-modify-write 文件操作配合 mtime/size/revision 校验；锁超时可诊断，不能静默覆盖。
- 验收：两个独立 Node 进程同时改标题、改 index、编辑消息时，不丢更新；锁残留可恢复且不会误删活跃锁。
- 实现：lockfile 带 heartbeat、stale lock 检测、PID 存活判断和超时诊断；双 Node 进程串行测试通过。

### P1-4 AI 标题生成和 rollback 缺少 compare-and-swap

- 状态：已完成
- 位置：`packages/server/src/services/conversation-title.ts`、`packages/server/src/cli/title-manager.ts`
- 问题：AI 调用或 rollback 期间用户通过 UI、CLI 或原生 `/rename` 修改标题时，旧操作可能覆盖新标题。
- 规则：以来源和 revision 判断，不使用“强标题/弱标题”覆盖规则。UI 手动标题和原生 `/rename` 都必须保持最高优先级的最新写入语义。
- 目标方案：记录操作开始时的标题/revision；写回只在 revision 未变化时执行；冲突返回 `409` 或 `skipped-conflict`；rollback 仅在当前标题仍等于报告中的 `generatedTitle` 时恢复；显式 `--force` 才允许覆盖。
- 验收：AI 生成期间手动改名、rollback 期间手动改名、UI 与 CLI 同时改名时，新手动标题始终保留。
- 实现：native 与 overlay 标题统一使用 `conversation-title:<id>` 锁和 compare-and-swap；AI 写回携带 `expectedTitle`，rollback 冲突标记 `skipped-conflict`，显式 `--force` 才覆盖。

### P1-5 Fresh 标题会话清理必须 fail-closed

- 状态：已完成
- 位置：`packages/server/src/services/conversation-title.ts`
- 问题：生成前快照失败时可能视为空集合；若本次没有精确 session ID，badge 扫描可能误删原有 fixed 会话。
- 目标方案：快照失败时禁止批量 badge 清理；仅允许按本次返回的精确 session ID 删除；报告区分精确清理、扫描清理和跳过清理。
- 验收：快照失败、CLI 超时、CLI 无 session ID、已有 fixed session 存在时，不删除调用前已有会话。
- 实现：快照失败时禁止 badge 扫描清理；有精确 session ID 时只删除本次辅助会话；已有 fixed 会话受保护。

### P1-6 Claude Code move 缺少完整 rollback

- 状态：已完成
- 位置：`packages/server/src/providers/claude-code.ts`
- 问题：transcript、session 目录、旧 index、新 index 依次操作，后续失败不会恢复前面步骤；批量 move 可能并发修改同一个 index。
- 目标方案：共享 mutation transaction；同一 index 串行锁；记录每一步并在异常时逆向恢复。
- 验收：每个步骤注入失败后，源文件、目标文件和 index 都恢复到一致状态；批量移动不丢 index 项。
- 实现：组合锁覆盖会话、源/目标 index 和文件目录；保存 index 原始快照并按逆序 rollback；目标 index 故障注入测试通过。

## P1/P2 缓存与数据源一致性

### P1-7 OpenCode source signature 忽略 WAL

- 状态：已完成
- 位置：`packages/server/src/providers/opencode.ts:384`、`packages/server/src/utils/cache.ts:645`
- 问题：只统计 `opencode.db` 主文件；新增会话或原生改名只写入 WAL 时可能长期命中旧缓存。
- 目标方案：signature 纳入 `-wal`/`-shm` 的 mtime/size，或查询数据库内最大更新时间和行数；signature 命中时仍保留有限强制刷新 TTL。
- 验收：只改变 WAL 时 UI 列表、标题和数量在刷新后可见。
- 实现：signature 纳入 `opencode.db-wal` 和 `-shm`，且 signature 相同最多复用 5 分钟后强制刷新。

### P2-1 数据库和 schema 错误不能伪装成空列表

- 状态：进行中
- 位置：各 provider、`packages/server/src/providers/codex-sqlite-client.ts`、`packages/server/src/utils/cache.ts`
- 问题：数据库 locked、损坏、权限不足或 schema 不兼容时大量 `catch` 返回 `[]`、`null` 或空对象。
- 目标方案：统一 provider error model，区分 unavailable、locked、corrupt、schema-incompatible、empty；路由返回明确 warning 和诊断日志。
- 验收：故意锁库、损坏数据库、删除表、权限拒绝时，UI 明确提示失败原因，不显示“没有记录”。
- 已完成：增加 `ProviderDataError`，区分 `unavailable`、`locked`、`corrupt`、`schema-incompatible`；OpenCode 不再把 schema/读取错误返回为空列表；列表 API 返回 `partialResults` 和具体 warning，详情错误可返回 `503`。
- 待完成：继续清理 Codex SQLite、Claude Code 和 iFlow 中仍会吞掉非预期错误的兼容性 `catch`，保留确有依据的降级路径。

## P2 性能

### P2-2 OpenCode 列表存在 N+1 查询

- 状态：已完成
- 位置：`packages/server/src/providers/opencode.ts:458`
- 问题：先列出全部 session，再对每个 session 分别读取 message 和 part；普通列表同时构建全文索引。
- 目标方案：批量读取 message/part；普通列表只取 metadata；搜索索引后台增量构建。
- 验收：固定 fixture 下 cold list、search 和 rebuild 达到设定阈值，并记录内存峰值。
- 实现：普通列表只读取 metadata 和 grouped message count；搜索使用两条批量 SQL 读取 message/part，消除 N+1；正文体积仅在搜索索引构建时计算。
- 实测：cold metadata 从中间版本 `10511 ms` 降至 `759.5 ms`，warm metadata `3.6 ms`。

### P2-3 只请求一个 provider 时仍刷新全部 provider

- 状态：已完成
- 位置：`packages/server/src/routes/conversations.ts:201`
- 问题：provider filter 应用前会 detect、signature 和刷新全部 provider。
- 目标方案：只刷新 active provider；facet 使用轻量缓存；provider 切换不触发无关 provider 全量索引。
- 验收：只请求 Codex 时不读取 Claude Code、OpenCode 和 iFlow 的完整数据源。
- 验证：路由测试确认 `provider=codex` 时 OpenCode `detect/list` 调用次数均为 `0`。

### P2-4 分页、过滤和排序没有下推到索引层

- 状态：待处理
- 位置：`packages/server/src/routes/conversations.ts:252-324`
- 问题：先取全部结果、全量解析标题和排序，最后才 `slice`。
- 目标方案：把 `limit`、`offset`、provider、project、model provider、sort 下推到 SQLite 索引查询。
- 验收：大数据 fixture 下第一页请求的读取行数和耗时随 page size 而不是总记录数增长。

### P2-5 Codex app-server 每次改名都重新启动

- 状态：待处理
- 位置：`packages/server/src/providers/codex-app-server.ts`
- 问题：每次标题修改都启动和销毁 app-server，批量操作成本高。
- 目标方案：长生命周期 client，串行请求，断线自动重启，空闲超时关闭；Windows 继续使用可靠的 process-tree kill。
- 验收：连续改名复用同一 app-server；连接异常后可以自动恢复；不会残留子进程。

## P2 架构与功能模型

### P2-6 统一 provider capability model

- 状态：已完成
- 位置：`packages/server/src/providers/types.ts`
- 问题：目前主要声明标题能力，消息编辑、消息删除、移动、metadata-only 等能力分散在 optional method、route 和 UI 判断中。
- 目标方案：统一声明 `canUpdateTitle`、`canGenerateTitle`、`canEditMessage`、`canDeleteMessage`、`canMoveConversation`、`canDeleteConversation`、`supportsMetadataOnly` 和 disabled reason。
- 验收：UI、API 和 CLI 都根据同一 capability model 决定是否开放操作。
- 实现：统一标题、消息编辑/删除、会话移动/删除和 metadata-only capability；API 强制校验，UI 根据同一 contract 隐藏或禁用操作；OpenCode 明确声明消息编辑/删除暂不支持。

### P2-7 拆分过大的模块

- 状态：待处理
- 主要文件：`codex.ts`、`claude-code.ts`、`cache.ts`、`ai.ts`
- 问题：provider 读取、索引、mutation、迁移、标题和缓存职责耦合，schema 演化时回归风险高。
- 目标方案：按 source reader、metadata index、message mutation、native title、migration transaction 拆分，保持 provider facade 稳定。
- 验收：拆分后 public behavior 和现有测试保持不变，模块职责和依赖方向清晰。

### P2-8 OpenCode 消息编辑/删除暂缓

- 状态：暂缓
- 原因：一条 UI 消息可能对应多个 SQLite `part`，直接删除 `message` 行可能破坏 tool、reasoning、step 结构。
- 推荐方案：后续按可见 `part` 实现，尽量对齐 OpenCode 官方 `part.update` / `part.delete` 语义，并兼容 legacy `message`/`part` 与新版投影表。
